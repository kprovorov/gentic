The primary way to configure the agent worker is with `gentic worker connect <code>`, which exchanges a single-use enrollment code for a stable worker id, API URL, and worker-specific credential. The CLI saves those values to a persistent config file on disk with owner-only permissions. Environment variables — including a `.env` file loaded at startup — are the alternative, and are the right choice for containers, CI systems, or local development where you manage secrets through the environment. When the same key appears in both sources, the environment variable takes precedence over the config file.

## First-run behavior

When you run a `gentic` command for the first time, the CLI checks whether the worker is ready before it continues. This onboarding gate runs for normal worker commands, including `gentic start` and `gentic run`. It does not run for `gentic worker connect`, `gentic onboard`, `gentic status`, `gentic doctor`, `gentic auth`, `--help`, or `--version`, so you can always connect a worker, resume setup, or inspect the CLI without completing onboarding first.

If the command is running in an interactive terminal and any required setup is missing, Gentic starts the first-run flow automatically. The flow has four steps:

1. **Gentic worker** — verifies that this machine has a stored worker id, API URL, and worker credential from `gentic worker connect <code>`. This is required.
2. **GitHub CLI** — checks that `gh` is installed and authenticated, and offers to install or run `gh auth login` when possible. This is required because agents use GitHub CLI access to open pull requests.
3. **Agent CLI** — checks both Claude Code and Codex. Both agent CLIs must be installed and authenticated because the worker can claim issues for either provider.
4. **Worker service** — shows a summary and asks whether to enable the background worker with `gentic start`. This step is optional; you can decline and run `gentic start` later.

For CI, containers, or other non-interactive environments, bypass the prompts by providing the required settings up front:

```bash
GENTIC_API_URL=https://app.gentic.chat/api/v1 \
GENTIC_WORKER_ID=<worker-id> \
GENTIC_WORKER_CREDENTIAL=<your-worker-credential> \
gentic run
```

You can also connect once, skip local onboarding, and resume setup later:

```bash
gentic worker connect <code> --no-onboard
gentic onboard
```

Non-interactive runs still require `gh`, Claude Code, and Codex to be installed and authenticated before the worker command starts. If any required item is missing, Gentic exits with the unmet requirements instead of prompting.

## Worker Enrollment via CLI

The recommended way to configure credentials is with `gentic worker connect <code>`. This command reads and writes an OS-appropriate config file — for example, `~/.config/gentic/config.json` on Linux — that persists across restarts without needing a `.env` file.

<Note>
  `GENTIC_WORKER_CREDENTIAL` is issued by the enrollment exchange. Do not reuse
  a shared API key. Losing the config file loses the local worker identity; the
  next enrollment creates a new worker instead of reclaiming by hostname.
</Note>

### Connect

Generate a worker enrollment code in the Gentic web app, then connect this machine:

```bash
gentic worker connect <code>
```

For a self-hosted or local API, override the initial exchange URL:

```bash
gentic worker connect <code> --api-url http://localhost:3000/api/v1
```

### Check authentication status

Display the currently configured API URL and a masked version of your worker credential:

```bash
gentic auth status
```

### Log out

Clear the stored credentials from the config file. Run with `--yes` (or `-y`) to skip the confirmation prompt:

```bash
gentic auth logout
gentic auth logout --yes
```

Logging out removes the local worker registration entries: `GENTIC_WORKER_ID`, `GENTIC_WORKER_CREDENTIAL`, `GENTIC_API_URL`, and `GENTIC_WORKER_SETUP_STATE`. Other settings stored in the config file — such as `GIT_REMOTE_BASE`, `WORKDIR`, and `POLL_INTERVAL_MS` — are preserved.

## Environment variables (alternative)

Environment variables give you fine-grained control over every configuration value and are an alternative to the persisted config file — useful for local development, containers, or CI systems where you manage secrets through the environment directly. Create a `.env` file in the directory where you run `gentic` and fill in the values for your environment:

```bash
# .env
GENTIC_API_URL=https://app.gentic.chat/api/v1
GENTIC_WORKER_ID=worker_id_from_enrollment
GENTIC_WORKER_CREDENTIAL=your_worker_credential_here
```

The full list of supported variables is below.

### Required

<ParamField body="GENTIC_API_URL" type="string" required>
  The Gentic API endpoint. Use `https://app.gentic.chat/api/v1` for the hosted service, or `http://localhost:3000/api/v1` when developing against a local web app instance.

```bash
GENTIC_API_URL=https://app.gentic.chat/api/v1
```

</ParamField>

<ParamField body="GENTIC_WORKER_ID" type="string" required>
  The stable worker id returned by `gentic worker connect <code>`. Keep it paired with its credential so service and process restarts preserve the same worker identity.

```bash
GENTIC_WORKER_ID=worker_id_from_enrollment
```

</ParamField>

<ParamField body="GENTIC_WORKER_CREDENTIAL" type="string" required>
  A worker-specific credential issued by the enrollment exchange. The hosted API verifies the worker credential and only returns issues that belong to its user.

```bash
GENTIC_WORKER_CREDENTIAL=your_worker_credential_here
```

</ParamField>

### Optional

<ParamField body="GIT_REMOTE_BASE" type="string" default="git@github.com:">
  The base URL prepended to each project's `owner/repo` path when the worker clones a repository. With the default value, a project stored as `acme/backend` is cloned from `git@github.com:acme/backend`.

Change this if your repositories are hosted on GitHub Enterprise, GitLab, or another Git provider:

```bash
GIT_REMOTE_BASE=git@github.mycompany.com:
```

</ParamField>

<ParamField body="MAX_CONCURRENT_ISSUES" type="number" default="1">
  The maximum number of issues this worker processes at the same time. Each active issue uses its own repository clone and realtime channel. Increase this only when the host has enough CPU, memory, disk, and agent-provider capacity.

```bash
MAX_CONCURRENT_ISSUES=3
```

</ParamField>

<ParamField body="WORKDIR" type="string" default="~/.local/share/gentic/workspaces (Linux)">
  The directory where the worker creates per-issue repository clones. Each issue gets its own subdirectory. If unset, the worker uses an OS-appropriate data directory determined by [`env-paths`](https://github.com/sindresorhus/env-paths):

- **Linux**: `~/.local/share/gentic/workspaces`
- **macOS**: `~/Library/Application Support/gentic/workspaces`

Override it to use a custom location, such as a dedicated volume with more disk space:

```bash
WORKDIR=/mnt/data/gentic-workspaces
```

</ParamField>

<ParamField body="POLL_INTERVAL_MS" type="number" default="3000">
  How often (in milliseconds) the worker polls the Gentic API for issues with `status = 'todo'` (or `status = 'held'` past their usage-limit reset time). The default of `3000` ms (3 seconds) works well for most setups. Increase this value to reduce API traffic on low-priority workers.

```bash
POLL_INTERVAL_MS=5000
```

</ParamField>

## Configuration precedence

The worker merges all configuration sources in the following order, with later sources winning:

1. **Config file** — written by `gentic worker connect <code>` (e.g. `~/.config/gentic/config.json`)
2. **`.env` file** — loaded from the working directory at startup
3. **Shell environment variables** — exported in the process environment at runtime

This means you can enroll the worker once with `gentic worker connect <code>` and use environment variables only for per-deployment overrides like `WORKDIR` or `POLL_INTERVAL_MS`.
